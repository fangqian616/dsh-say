# 人设写法指南

一份好人设是**可执行的**，不是形容词堆砌。"性格开朗"改不了任何输出；"每条不超过 80 字、不许用感叹号"能。

## 结构

每个角色一个文件，放在 `soul/<名字>.md`，建议包含五节：

| 小节 | 作用 | 必须具体到 |
|---|---|---|
| **身份** | 这个角色怎么理解"工作"这件事 | 一个比喻或立场，不要履历 |
| **语气** | 措辞与称呼 | 用/不用哪些词、怎么称呼对方 |
| **节奏** | 长度与断句 | 字数上限、一句几个意思 |
| **禁忌** | 硬约束 | 明确禁止的写法 |
| **示例** | 同一件事的平实版 vs 角色版 | 至少一组对比 |

**示例那一节最重要。** 抽象描述每个人理解都不同，一组对比例子能立刻对齐。

## 三条硬规则

**1. 人设不覆盖事实。**
人设只改措辞。数字、结论、成功/失败状态必须与文字汇报完全一致。
写人设时把这条写进去，否则模型容易为了"像角色"而含糊。

**2. 坏消息让位于清晰。**
在禁忌或示例里明确：失败与风险优先用平实语气说清楚。
一个念不清楚故障的角色声音，是负资产。

**3. 长度写死上限。**
不写上限，模型会按文字的篇幅生成语音 —— 一份 500 字的汇报念出来要一分半。
建议 **100 字 / 15 秒** 上限，长汇报只念结论。

## 反例

| 写法 | 问题 |
|---|---|
| "性格活泼可爱" | 不可执行，改不动输出 |
| "像动漫角色一样说话" | 太模糊，每次结果都不一样 |
| "要幽默" | 幽默在技术汇报里通常是灾难 |
| 没有任何禁忌 | 模型会自行发挥，往往加上"呢""哦"和感叹号 |
| 只写身份不写节奏 | 语音会过长 |

## 正例（节选）

```markdown
## 语气
- 口语、短句、节奏快。先给结论，不铺垫。
- 可以用技术比喻：关卡、读条、走位。
- 不卖萌、不撒娇、不叠语气词。

## 禁忌
- 没验证过的事不说"搞定"。不确定就说"还没确认"。
- 失败就直说，别绕。
- 不用"呢""哦""啦"。

## 示例
平实：已经删除了那五个文件，释放了 5.3 GB。
角色：五个文件清掉了，腾出五点三G。这一关过了。
```

## 换声线

`soul/voice-pack.json` 的 `pack` 字段决定用哪个声线包：

```json
{ "pack": "my-voice", "speed": 1.0 }
```

`pack` 留空 → 用插件配置的默认值；插件也没有 → 退回系统语音。

声线包本身不在这个仓库里（见 [voice/README.md](../../../voice/README.md)）。**人设文件和声线包是分开的**：你可以用同一个人设配不同声线，也可以同一个声线换不同人设。
